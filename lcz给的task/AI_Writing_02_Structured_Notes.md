## 一、会议要解决的核心问题

讨论围绕两个相互关联但不可混为一谈的目标：

1. **写作质量**：AI写出来的文字为什么显得空泛、刻意、重复，甚至带有生成过程的痕迹？如何识别这些现象，又怎样在不损伤真实逻辑的条件下修改？
2. **文档工程**：即使文字本身写好了，Markdown、Word、参考文献、字体、行距、图表等格式仍可能不符合目标规范。是否能把明确的格式要求转化为可复用的配置与操作？

后半段又引出第三个工程问题：**角色和上下文管理**。当AI在写作者、审稿人、资料整理者等角色间切换时，如何让角色约束既准确生效，又不使提示词过度膨胀？

## 二、AI写作问题的分类记录

### 1. 过度名词化：把过程包装成概念

- **讨论时段**：00:00:44—00:03:22；00:16:44—00:18:54；00:33:11—00:34:22。
- **典型表现**：原本是“先A、再B、后C”的过程，却被命名为“A—B—C三重机制”“三维”“三阶”“××体系”等；或者把具体差异包装成“缺口的性质是提问方向的偏移”。
- **问题所在**：名词标签未必提供额外信息，甚至可能遮住过程、变量、条件以及具体差异。某些抽象句子需要随后花更多文字解释自己。
- **讨论中的处理设想**：建立“数字＋重/维/阶”等标志性模式和常见表达清单；发现疑似问题后返回上下文，把有意义的过程或差异直接写清楚。
- **边界**：不能仅因出现“三维”“体系”“机制”等词就判错，亦不能机械删除概念词。需要判定该概念是否具有明确定义、是否承载必要信息。

### 2. 逻辑形式化：看似有链条，实际未说明联系

- **讨论时段**：00:00:44—00:03:34。
- **表现**：AI积极使用“先—再—后”“A—B—C”等显式逻辑框架，却没有交代为何从A过渡到B、为何B导致C。
- **核心疑问**：怎样区分“逻辑结构的外形”与“由事实、机制、条件支撑的推理”？怎样让AI沿着人的研究思路展开？
- **状态**：明确提出问题；没有形成已验证的解决方案。

### 3. 符号与标点滥用

- **讨论时段**：00:03:34—00:07:43；00:19:58—00:22:01。
- **候选现象**：把文字中的“不同于”写成“不等于”符号；无必要的引号、括号、破折号、箭头、间隔点；在前后应自然连贯的句子间强行使用冒号。
- **关于冒号的讨论**：冒号可能把本来连贯的论述拆为“前面下定义/概括，后面堆解释”的形态。部分实例通过改为逗号或重写整句会更自然。
- **形成的明确约束**：**不应写成“匹配所有冒号→统一删除”的规则。** 必须根据冒号是否用于引出解释、列举、引用或段内逻辑衔接作判断。
- **延伸要求**：文本修订后还应再检查一次，确认规则本身没有制造断句和逻辑问题。

### 4. 语义重复、元叙述与作者越位

- **讨论时段**：00:23:07—00:25:37；00:27:02—00:28:54。
- **表现一：重复**：总括句、提示句与后文实际分析所传递的信息几乎相同。
- **表现二：元叙述/作者越位**：作者中途跳出论证，对自己的分析作“已经说明”“上述分析很重要”等评价；结论或研究缺口靠提示语提醒读者，而非自然推出。**“元叙述”是板书可核实的现场术语**，不是原语音识别的“原叙述”。
- **表现三：过度强调**：用排比、对照或强烈提示语营造重要感。
- **分类提醒**：去掉重复语句不一定消除“作者越位”；过度强调也不等同于纯粹的语义重复。需要分别诊断。
- **证据缺口**：排比问题在会上没有找到足够清楚的现成例句，应先补案例。

**板书编号补充**：现场并非只列出大类，还试图将“符号化表达（非必要）”“概念堆叠（压缩判断）”“元叙述”“排比式强调”作为不同问题条目。这说明后续资料库应保留原编号与名称，再给每条建立可交叉的标签，避免把所有不自然表达都合并成“AI味”。其中一条编号旁字迹仍不清，不据此增加新术语。

### 5. 防御性写作与内部决策痕迹外露

- **讨论时段**：00:24:21—00:25:37；00:38:09—00:40:42。
- **表现**：将内部修改过程、历史选择、限制条件或“某部分已在某章节说明”一类说明直接放到读者面前；试图让读者知道作者已经考虑所有可能质疑。
- **提出的解释**：AI不清楚当前写作身份、读者对象与最终文本用途，或者过度使用所有可用上下文。
- **处理方向**：明确最终写作角色与交付对象，在编辑时区分“供作者内部决策的信息”和“读者真正需要阅读的论述”。
- **状态**：原因仍属讨论性假设；与角色路由的关系需要通过例文测试。

### 6. 材料强行嵌入与引用污染

- **讨论时段**：00:38:09—00:39:12。
- **表现**：AI得到新材料后，为了证明自己利用了它，忽视语段原有论证结构，把资料、跨段信息或其他文件的内容强行塞进文本。
- **风险**：段落离题、材料与判断不匹配、叙述冗长、引用不服务于论证。
- **方向**：不能以“是否使用了全部输入材料”作为质量标准；应检查信息与段落目标之间是否存在必要联系。

### 7. 学术判断过强与价值评估失衡

- **讨论时段**：00:28:54—00:30:59；00:34:22—00:37:46。
- **重点词句**：“填补学术空白”“已经非常成熟”“几乎全部”“红海/蓝海”等。
- **典型风险**：检索有限文献就断言研究空白；阅读若干论文就宣布某方向研究“成熟”；在证据不足时作范围过大的概括；把“研究较少”直接等同于“更有价值”。
- **重要区分**：合理的学术自信不是把表述一律改得含糊；学术谨慎要求判断的强度与可核查证据相匹配。
- **会议中出现的纠偏**：“政策工具箱”可能是已被广泛使用的术语，不能和无根据的概念包装一概而论。

## 三、文档排版与自动化讨论

### 1. 目标与既有路径

**时间**：00:03:34—00:16:44；00:53:48—00:56:58。

当前谈到的一种工作流是：Markdown写作→Pandoc转换DOCX→Word样式集修改。它的优点是初始样式相对统一，改动某类标题或正文可批量生效；问题是可能需要二次编辑，且表格、公式、行距等细节仍存在误差。

讨论中还提到Office相关MCP、DOCX底层XML、Word样式和某些编辑工具。是否需要逆向Office存在分歧；有人认为应先掌握公开规范和现有工具能力，避免重复实现。

### 2. 拟整理的规则范围

| 规则层次 | 当场提到的内容 | 整理时的注意事项 |
|---|---|---|
| 文档整体 | 规范来源、页边距、中文或英文标准 | 不同学校、期刊、竞赛模板不可混为一套 |
| 标题 | 层级、编号、字体、字号、颜色 | 识别冲突或重复条款，避免编号失配 |
| 正文段落 | 首行缩进、行距、段距 | 区分磅值、倍数及单位；核查适用范围 |
| 页眉页脚 | 多项信息的对齐 | 原稿页眉数字识别存疑，需查具体例子 |
| 图表与公式 | 位置、题注、表格内容、不同场景的样式 | 图表规范往往比正文更细 |
| 参考文献 | 各竞赛或学术规范的差异 | 引用格式要建立独立规则，不宜隐含在正文样式中 |
| 中英文字符 | 中西文字体、引号、标点 | 字符本身与显示字体不是同一问题 |
| 格式来源 | Markdown结构、DOCX样式 | 源文件错误也会造成导出样式不一致 |

### 3. 可以保留的技术思路

- 建立一份**基础样式（base）**，用于常见正文，而不是每次从空白文档开始。
- 将格式要求拆成逐项条款，建立“规范要求—可配置属性—实现方法”的映射。
- 新模板导入时，先与基准规则比较，找出差异、冲突和未覆盖条款。
- 把标题、图、表、公式、引用等拆成独立模块，减少互相影响。
- 将Markdown源文本的结构校验放在导出前，不假定Pandoc能修复所有输入错误。
- 对字符编码、中英文引号、Office样式与Pandoc能力进行**工具边界核查**，不要依赖未经验证的能力预期。

板书进一步确认了这一流程的具体表达：**`.md → Pandoc → .docx → 样式集调整`**，同时把“中文/英文规范”与“标题、作者、正文、图表、间距”等列为格式检查对象。板书下方还有行距单位“磅”“倍”和类似`12pt`的数字；这些是现场讨论实例，**不能直接写成通用模板参数**。

### 4. 尚未解决的取舍

1. 在Pandoc配置＋样式集基础上迭代，还是开发新的编辑层？
2. 能否做到“一次处理全部格式”，或者仍需要审阅和微调？
3. 各类竞赛、论文模板之间的冲突如何表达？
4. 怎样确保处理第一批和后续追加的内容时采用相同的样式？

**纪要结论**：会议提出了模块化规则库的方向，但没有实际完成或验证通用自动排版工具。

## 四、Agent角色与上下文管理

**主要时段**：00:39:12—00:47:30。

### 讨论的两条路径

**路径A：项目级规则与动态路由。** 在项目说明（讨论中提到AGENTS.md及类似配置）内维护任务类型与角色要求。每个任务开始时，根据当前目标选定“写作者、审稿人、教师、学生”等角色，而不是始终将所有角色加载进上下文。

**路径B：轻量Prefix＋外部角色片段。** 借鉴Snippet/Prefix插件机制，保持较短的入口指令，按需调入外部文件中的角色定义。有发言者希望角色选择由系统自动判断，而非每次手工选择。

板书左上角还画了`~/.config/opencode/`与`Prefix → … .md`的连接，左侧另圈出近似`Agent.md`并注“角色”。这加强了“把角色定义与会话前缀分离”的解读，但不表示OpenCode的配置结构或插件名称已经得到验证。

### 双方实际关注的问题

- 项目级与全局规则如何分工。
- 常驻角色是否会增加无关上下文。
- 同一项目多轮对话、并行任务如何切换角色。
- 新增角色是否必须改写所有项目文件。
- 有无可复用的现成插件或方案，避免重复造轮子。

“常驻子代理”亦被提及，但没有现场验证。所谓关键词注入插件的具体名称、可用性与自动选择能力，也未得到核实。

## 六、形成的认识、分歧与待验证假设

### 较明确的共同认识

1. AI写作质量不能只靠一张“禁用词表”改善。词句应结合上下文判断；错误的机械规则反而会破坏语言与逻辑。
2. 写作问题不是单一层面：概念包装、逻辑空洞、信息塞入、作者越位、学术判断过强各有区别，也存在交叉。
3. 需要持续积累**原句、上下文、问题诊断、修改方案**四类材料，才能形成可检验的处理方法。
4. 文档排版应先建立统一基础样式与规则描述，后续再适配不同格式来源。
5. 项目体量不小，初期应以整理记录、案例库和规则库为主，不宜把未经验证的设想直接当成产品能力。

### 尚有分歧或证据不足的内容

- 冒号是否应当被一般性地限制使用；具体语境仍决定其必要性。
- Word/DOCX自动化究竟需要新开发，还是组合现有工具已足够。
- 角色切换最好交给项目配置、插件前缀还是独立代理路由。
- “AI经常使用某类表达”的频率判断目前主要来自经验；尚未进行系统抽样和统计。
- 插件、工具和Office相关实现的能力未现场核实。

## 八、信息质量与使用限制

- **说话人无法分离**：原转写全部标记为Speaker 1。不要用本纪要推断具体个人作出的承诺。
