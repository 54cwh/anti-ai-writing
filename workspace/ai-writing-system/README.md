# AI Writing System

**Beyond Humanization. Toward Better Reasoning and Writing.**

一个以逻辑实质、认识形成和任务协作为核心的 AI 写作系统。

---

## 1. Introduction

AI Writing System 旨在解决 AI 写作过程中反复出现的深层问题。

我们不满足于通过调整句式、替换词汇、增加提示词限制等方式，让 AI 生成的文本在表面上更接近人类写作。

我们希望解决的是：**为什么 AI 能够生成形式完整、语言流畅的文本，却经常无法让读者真正理解它想表达什么。**

在实际使用中，我们观察到，AI 写作存在一些反复出现的问题：

- 结论先行，通过大量数据和抽象表达制造论证已经完成的假象。
- 省略必要的解释过程，直接从前提跳到结论。
- 能够组织形式完整的论证，却缺乏真正成立的逻辑联系。
- 对因果关系缺乏充分解释，无法说明事物为什么发生、如何发生。
- 主动引入不必要的问题、反对意见和限定条件。
- 将不确定性处理为免责声明和防御性表达。
- 在缺少必要信息时自行推测，使用看似合理的内容填补逻辑空白。
- 在局部修改中不断产生新的问题，陷入反复优化的循环。

这些问题并不只是语言风格问题。

典型 AI 句式、过度抽象、机械化表达等现象，可能只是更深层问题在语言层面的表现。

因此，本项目将研究和解决问题的重点放在写作过程本身：从任务理解、信息获取、认识形成，到逻辑组织、文本生成和独立评价。

## 2. Our Understanding of AI Writing Problems

我们目前形成了几个重要的初步认识。

### 2.1 Form Is Not Substance

AI 有时能够使用形式逻辑的骨架，却没有充分处理逻辑的实质。

它可以生成：

- 观点；
- 论据；
- 过渡；
- 总结；
- 反驳；
- 限定。

但这些形式要素的存在，并不意味着它们之间的关系真正成立。

一段文字可以拥有完整的论证结构，却依然缺乏必要的解释。

我们尤其关注：形式上的连贯，为什么经常不能转化为认识上的连贯？

### 2.2 Conclusion Substitution

AI 经常倾向于直接制造结论，而不是解释结论如何形成。

例如：

```text
实际需要的解释：

条件 A
  ↓
发生过程 B
  ↓
形成机制 C
  ↓
产生结果 D
```

AI 有时会将其压缩为：

```text
条件 A
  ↓
结果 D
```

随后通过增加抽象词汇、数据和总结性判断，使文本看起来已经完成了解释。

但读者真正需要的中间过程仍然缺失。

我们需要研究：什么时候可以合理压缩解释，什么时候压缩会破坏论证的完整性。

### 2.3 Insufficient Causal Explanation

我们特别关注 AI 在日常解释性写作中的因果问题。

这里的因果并不局限于经济学、计量经济学或科学研究中的因果识别。

它还包括普通写作中经常需要回答的问题：

- 为什么某件事情会发生？
- 一个因素究竟通过什么过程影响另一个因素？
- 某种变化是如何产生的？
- 不同条件之间存在什么关系？
- 为什么某个结果能够从前面的过程产生？

我们关注的是因果解释本身是否充分，而不只是句子中有没有出现「因为」「因此」「导致」等词语。

### 2.4 Relevance Is Not Necessity

AI 有时会主动引入一个并非当前讨论重点的问题，再对这个问题进行充分回应。

这些内容可能在逻辑上成立，却不一定有必要出现在当前文本中。

我们需要让模型区分：

- 可能相关的问题；
- 会影响核心判断的问题；
- 当前必须回答的问题；
- 理论上存在但当前无需展开的问题。

写作不仅需要知道应该讨论什么，也需要知道什么不应该进入当前论述。

### 2.5 Defensive Writing and Uncertainty

AI 有时会把不确定性处理成大量限定词、免责声明和防御性表达。

但不确定性本身并不是缺陷。

真正需要解决的是：

- 不确定性究竟来自哪里？
- 哪个判断尚未得到充分支持？
- 哪个过程缺少必要信息？
- 哪些结论可以明确表达？
- 哪些内容必须保留为待验证状态？

我们不希望通过禁止不确定性表达来解决防御性写作，而是希望模型能够准确识别和处理不确定性。

### 2.6 Information Deficiency

AI 并不总是具备独立完成任务的全部条件。

有时候，它缺少必要资料；有时候，它没有正确调用已经存在的信息；有时候，它并不理解用户真正想表达什么。

这些情况不能全部通过改善逻辑或增加提示词解决。

模型应该能够判断：

- 是否需要检索资料？
- 是否需要读取已有文件？
- 是否需要询问用户？
- 是否需要调整任务范围？
- 是否应该承认当前问题无法得到确定答案？

我们不希望 AI 用语言生成能力掩盖信息不足。

## 3. Design Philosophy

本项目遵循以下设计原则。

### 3.1 Understand Before Writing

正式写作之前，先理解任务。

明确写作目的、文本功能、目标读者和论述边界。

### 3.2 Reason Before Expressing

先形成必要的认识，再组织语言。

不能用形式上的完整代替实质上的理解。

### 3.3 Diagnose Before Modifying

发现问题后，先判断问题来源，再决定修改方式。

不要把所有缺陷都归结为语言表达问题。

### 3.4 Retrieve or Ask, Rather Than Invent

缺少信息时，优先检索或询问。

不允许为了完成文本而自行编造事实、机制和用户意图。

### 3.5 Relevance Before Completeness

不追求把所有相关问题都写进正文。

内容是否有必要出现，应当取决于它是否服务于当前写作任务。

### 3.6 Preserve Uncertainty Without Defensive Writing

准确表达判断的成立程度。

不夸大结论，也不通过过度限定削弱已有充分依据的判断。

### 3.7 Stop Local Optimization When Necessary

当修改反复产生新问题时，允许停止当前方案。

寻找推导环节的漏洞，在原有优化循环之外重新讨论问题。

### 3.8 Continuous Learning

保留成功案例、失败案例、反例和实验结果。

未经验证的观察不能直接转化为永久规则。

## 4. System Architecture

本项目采用多代理协作架构。

一个主代理负责理解任务、初步分析、动态提示词生成和代理调度；四个子代理分别承担写作、资料研究、逻辑分析和独立评价。

```text
                  USER
                    |
                    v
          +--------------------+
          |  PROMPT ARCHITECT  |
          |      主代理        |
          |                    |
          | 任务理解            |
          | 初步逻辑分析        |
          | 信息充分性判断      |
          | 动态提示词生成      |
          | 代理调度            |
          | 最终决策            |
          +---------+----------+
                    |
          +---------+---------+
          |         |         |
          v         v         v
      RESEARCHER  LOGIC     WRITER
                  ANALYST
          |         |         |
          v         v         |
        资料报告  逻辑报告     |
          |         |         |
          +---------+---------+
                    |
                    v
             PROMPT ARCHITECT
                    |
                    v
                  WRITER
                    |
                    v
                 TEXT
                    |
                    v
                EVALUATOR
                    |
                    v
             PROMPT ARCHITECT
                    |
              +-----+-----+
              |           |
              v           v
             交付       重新处理
```

### Agents

| Agent | Responsibility |
|---|---|
| Prompt Architect | 任务理解、初步分析、提示词设计、代理调度与最终决策 |
| Writer | 正式写作、文本组织、表达与修改 |
| Researcher | 资料检索、信息补充与事实核查 |
| Logic Analyst | 写作前的认识分析、推理关系与因果解释 |
| Evaluator | 写作后的整体质量评价与独立审查 |

代理之间采用集中协调、按需调用的方式。

子代理可以提出质疑、请求资料和提交替代方案，但不能未经主代理协调就改变用户的核心任务。

### Prompt Architect

Prompt Architect 是系统的控制中心。

它不只是提示词生成器，还必须具备初步分析能力。

它负责判断：

1. 当前任务真正需要完成什么？
2. 现有信息是否充分？
3. 当前任务存在什么逻辑难点？
4. 是否需要调用专业代理？
5. 应该如何设计写作提示词？
6. 最终文本是否真正完成了任务？

### Shared Knowledge Base

所有代理共享知识库，并根据任务需要读取相关内容。

知识库用于积累：

- 写作方法；
- 逻辑知识；
- 因果解释；
- 问题案例；
- 失败案例；
- 反例；
- 提示词实验；
- 系统设计决策。

共享知识不等于共享全部上下文。每个代理只需要读取与当前任务相关的内容。

## 5. Workflow

系统的基本工作流程如下：

```text
01. TASK UNDERSTANDING
    理解用户意图与文本功能
             |
             v
02. PREPARATION
    判断信息充分性
    形成初步认识
    识别逻辑难点
             |
             v
03. PROMPT CONSTRUCTION
    动态设计适配任务的提示词
             |
             v
04. WRITING
    Writer 正式执行写作
             |
             v
05. EVALUATION
    Evaluator 独立评价
             |
             v
06. REVISION
    根据实际问题选择修改方式
             |
             v
07. ESCALATION
    必要时暂停并重新定义问题
             |
             v
           DELIVERY
```

并非所有任务都需要执行全部阶段。

简单任务可以直接进入写作；复杂任务则需要更充分的准备、分析和评价。

系统应当根据实际任务决定工作深度，而不是机械执行固定流程。

## 6. Evaluation

本项目不以文本是否具有某种典型的「人类写作风格」作为主要评价标准。

我们更关注文本是否真正完成了写作任务。

主要评价维度包括：

| Dimension | Evaluation Focus |
|---|---|
| Task Fulfillment | 是否准确完成用户要求 |
| Logical Integrity | 论证关系是否成立 |
| Causal Explanation | 必要的因果过程是否得到解释 |
| Information Fidelity | 是否准确使用已有材料 |
| Relevance | 是否存在不必要的论述扩张 |
| Uncertainty Calibration | 是否准确表达判断边界 |
| Global Coherence | 整体认识与论述是否连贯 |
| Readability | 读者能否真正理解文本 |

我们尤其重视修改的副作用。

解决一个问题，不应以制造另一个问题为代价。

例如，改善论证完整性不应该导致过度解释；保留不确定性不应该自动演变成防御性写作。

## 7. Development Approach

本项目采用问题驱动、案例验证和持续迭代的研发方式。

### Stage 1: Architecture

确定代理职责、协作关系、信息传递方式和共享知识库。

### Stage 2: Minimum Viable System

实现最基本的多代理工作流程，验证 Prompt Architect 的任务分析与动态提示词设计。

### Stage 3: Problem-oriented Testing

围绕真实 AI 写作问题建立测试案例。

初期重点包括：

- 结论替代过程解释；
- 因果说明不足；
- 推理跳跃；
- 整体论证割裂；
- 自发引入无关反对意见；
- 防御性写作；
- 信息不足时自行补全；
- 局部优化循环。

### Stage 4: Evaluation and Iteration

比较不同工作方式的结果：

- 直接生成与写作前准备；
- 固定提示词与动态提示词；
- 单代理与多代理协作；
- 普通修改与逻辑诊断后修改。

通过对照案例、反例和回归测试，判断系统是否真正改善了文本。

### Stage 5: Continuous Improvement

根据测试结果调整代理职责、工作流程、提示词和知识库。

不将未经验证的假设直接固化为规则。

---

## 8. Non-goals

本项目不以以下目标为主要方向：

- 机械消除所有 AI 典型句式；
- 建立庞大的禁用词和禁用表达清单；
- 让所有文本都遵循同一种写作风格；
- 强迫每篇文章都进行复杂的逻辑分析；
- 强制所有观点寻找反对意见；
- 通过增加免责声明实现表面严谨；
- 让所有任务都经过全部子代理；
- 无论信息是否充分，都生成看似完整的答案。

我们不追求让 AI 永远给出答案。

我们希望它知道什么时候应该写、什么时候应该查、什么时候应该问，以及什么时候应该停下来重新思考。

## 9. Project Status

**Current Stage: Initial Architecture Design**

目前已经形成初步的项目定位、问题认识、代理架构和基本工作流程。

以下内容仍然需要进一步研究和验证：

- 逻辑实质改善是否能够自然减少防御性写作；
- 动态提示词是否能够稳定改善复杂写作任务；
- 写作前的逻辑分析能够在多大程度上减少推理缺陷；
- 多代理协作是否能够带来超过单代理的实际收益；
- 如何识别和控制局部优化产生的副作用；
- 如何建立可靠、可重复的写作质量评价体系。

这些问题不会被预先当作已经解决的事实。

它们将成为后续实验和系统迭代的研究对象。

---

## 10. Core Mission

我们不希望 AI 只是学会如何把话说得更漂亮。

我们希望它能够：

- 理解自己正在解决什么问题；
- 知道自己的判断建立在什么基础上；
- 解释必要的逻辑与因果关系；
- 识别哪些信息尚未获得；
- 区分真正重要的问题与无关扩展；
- 准确处理不确定性；
- 在方法失效时停止并重新思考。

**The goal is not to make AI sound more human. The goal is to make AI reason, understand, and write better.**
