# AI Writing System
## System Architecture Overview

**Version:** 0.1  
**Status:** Initial Design

---

# 1. 项目定位

AI Writing System 是一个以 Prompt Architect 为主代理，通过动态提示词设计、专业子代理协作、信息获取和独立评价，完成复杂写作任务的智能写作系统。

本系统不以模仿人类写作风格、消除典型 AI 句式或增加文本规则为主要目标，而是关注写作过程中更深层的问题：

- 是否正确理解用户的写作意图？
- 是否掌握完成任务所需的信息？
- 是否形成了足以支撑写作的认识？
- 是否正确处理材料、概念和论证之间的关系？
- 是否充分解释必要的推理与因果过程？
- 是否区分了必要讨论与无关扩展？
- 是否能够准确处理不确定性？
- 是否能够识别自身方法的局限，并在必要时停止当前方案？

系统的核心目标是：

**让 AI 不再仅仅追求生成一篇形式完整的文本，而是能够判断完成写作任务需要什么条件，并主动建立这些条件。**

# 2. 核心设计理念

## 2.1 写作不是单纯的语言生成

写作质量受到多个环节共同影响。

本系统将写作任务理解为一个涉及任务理解、信息获取、认识形成、逻辑组织和语言表达的综合过程。
即写作任务 → 任务理解 → 信息获取 → 认识形成 → 逻辑组织 → 语言表达 → 文本输出
以上是主要工作环节，并非严格的单向因果链。不同环节可以相互反馈。

例如，写作过程中发现概念不清，可能需要重新分析材料；逻辑分析发现信息不足，则需要重新检索或询问用户。

## 2.2 优先处理问题的实质，而不是表面特征

系统不应将 AI 写作问题简单转化为禁止使用某些词语、句式或表达方式的规则。

例如：

- 「规矩立住了」不应直接被列入禁用表达。
- 「形成了有效闭环」不应被机械判定为错误。
- 防御性写作不应简单通过删除免责声明解决。
- 结论先行不应被视为所有文体中的缺陷。

系统需要结合具体语境，判断表达背后是否存在概念不清、过程缺失、推理跳跃或任务理解错误。

**评价表达是否恰当，应当回到表达所承担的实际任务。**

## 2.3 不把信息缺失当成推理问题

当模型无法解释某种现象时，需要区分：

- 模型尚未找到正确的分析方法。
- 当前材料缺少必要信息。
- 用户的真实意图尚不明确。
- 当前问题本身还没有得到充分研究。

不同问题需要不同的处理方式。

```text
             发现问题
                |
                v
           判断问题来源
                |
      +---------+---------+
      |         |         |
      v         v         v
   推理不足   信息不足   意图不明
      |         |         |
      v         v         v
   重新分析   检索资料   询问用户
```

禁止为了完成文本而自行编造缺失的事实、机制或用户意图。

## 2.4 相关性不等于必要性

模型能够联想到某个问题，不意味着这个问题必须进入正文。

系统需要区分：

- 与当前主题相关的问题。
- 对核心论点具有实质影响的问题。
- 当前文本必须回答的问题。
- 虽然可能成立，但当前没有必要讨论的问题。

尤其需要防止模型自发制造无关反对意见、过度扩大讨论范围，以及为了显得严谨而不断添加限定条件。

## 2.5 允许停止，而不是无限局部优化

当修改不断产生新问题时，系统不应默认继续增加规则。

需要判断：

1. 当前方法是否合理？
2. 问题是否来自执行偏差？
3. 提示词是否存在设计缺陷？
4. 是否缺少必要信息？
5. 原有问题定义是否存在错误？

当现有方案无法有效解决问题时，允许暂停，并在原有优化循环之外重新讨论。

核心原则：

**找到环节的漏洞，必要时跳出原有框架重新分析。**

## 2.6 建立共享知识，而不是建立相互隔离的代理

所有代理都可以按需访问共享知识库。

知识库记录经过整理的写作方法、逻辑知识、问题案例、实验结果和设计决策。

代理可以提交新的观察，但不能将未经验证的观察直接转化为强制规则。

# 3. 系统代理架构

系统采用一个主代理和四个子代理。

| 代理 | 类型 | 主要职责 |
|---|---|---|
| Prompt Architect | 主代理 | 任务理解、初步逻辑分析、提示词设计、代理调度、最终决策 |
| Writer | 子代理 | 正式写作、文本组织、修改与表达 |
| Researcher | 子代理 | 资料检索、信息补充、事实核查 |
| Logic Analyst | 子代理 | 深度认识分析、论证关系分析、逻辑缺口识别 |
| Evaluator | 子代理 | 写作后的独立评价、整体质量审查 |

## 3.1 Prompt Architect：主代理

Prompt Architect 是整个系统的控制中心。

它不只是提示词生成器，还承担初步分析和任务规划。

主要职责：

1. 理解用户的真实写作意图。
2. 判断文本在整体文章中的功能。
3. 判断当前信息是否足以完成任务。
4. 对材料、概念和核心论点进行初步逻辑分析。
5. 判断是否需要调用其他子代理。
6. 根据任务生成适配的提示词。
7. 协调代理之间的分歧。
8. 根据评价结果决定是否修改、补充信息或重新规划。
9. 负责最终任务交付。

特别强调：

Prompt Architect 必须具备一定的独立分析能力，不能把所有逻辑问题都交给 Logic Analyst。

它需要先形成自己的初步认识，才能判断 Logic Analyst 应该重点研究什么。

## 3.2 Writer：写作代理

Writer 是正式文本的主要生产者。

主要职责：

- 理解任务说明。
- 组织文章结构。
- 形成段落之间的合理关系。
- 展开必要的解释。
- 处理材料与结论之间的关系。
- 选择适当的语言和表达方式。
- 根据反馈修改文本。

Writer 拥有以下权利：

1. 对任务说明提出质疑。
2. 指出信息缺口。
3. 请求 Researcher 补充资料。
4. 指出提示词中的矛盾。
5. 提出替代论证或写作方案。
6. 在发现实质性问题时暂停当前写作。

但 Writer 不得未经 Prompt Architect 协调，自行改变用户的核心写作目标。

Writer 可以提出替代方案，由主代理判断是否采纳。

## 3.3 Researcher：资料研究代理

Researcher 负责解决信息获取问题。

主要职责：

- 检索外部资料。
- 搜索共享知识库和已有文件。
- 核实事实。
- 寻找支持或反驳相关判断的证据。
- 识别资料之间的矛盾。
- 明确现有资料无法回答的问题。

Researcher 不负责替作者形成最终观点。

检索到相关资料，不等于论证已经成立。

其输出应明确区分已确认事实、资料支持的判断、存在争议的信息和仍然缺失的信息。

## 3.4 Logic Analyst：逻辑分析代理

Logic Analyst 主要负责写作前的深度认识与论证分析。

它与 Prompt Architect 的区别在于：

- Prompt Architect 负责初步理解和判断，决定需要研究什么。
- Logic Analyst 负责对指定问题进行更深入、相对独立的分析。

主要职责：

1. 分析核心概念及其边界。
2. 分析材料之间的关系。
3. 检查论证链条。
4. 识别推理跳跃和隐藏前提。
5. 分析必要的因果关系。
6. 检查是否存在结论替代过程解释。
7. 识别不必要的反对意见和论述扩张。
8. 判断不确定性具体位于哪个环节。
9. 提出竞争性解释。
10. 指出需要进一步检索或询问的信息。

Logic Analyst 不负责正式写作，也不能凭空填补事实缺口。

它的主要价值是帮助系统在动笔之前形成更可靠的认识。

## 3.5 Evaluator：独立评价代理

Evaluator 主要负责写作后的整体质量评价。

它不直接接管 Writer 的工作，也不负责重新设计整个写作任务。

主要职责：

- 检查文本是否完成用户要求。
- 检查核心认识是否准确。
- 检查论证是否成立。
- 检查必要解释是否充分。
- 检查是否存在无依据的推论。
- 检查是否引入不必要的问题。
- 检查不确定性表达。
- 检查整体组织和语言质量。
- 检查修改是否引入新的问题。

Evaluator 应尽量独立于 Writer 的生成过程，避免仅仅认可 Writer 自己的判断。

它提交评价报告，由 Prompt Architect 决定后续处理。

# 4. 代理之间的工作关系

```text
                       USER
                         |
                         v
              +----------------------+
              |   PROMPT ARCHITECT   |
              |       主代理         |
              +----------+-----------+
                         |
                  理解任务与初步分析
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
         RESEARCHER  LOGIC ANALYST  WRITER
             |           |           |
             |           |           |
             v           v           |
         资料报告     逻辑报告        |
             |           |           |
             +-----------+-----------+
                         |
                         v
              +----------------------+
              |   PROMPT ARCHITECT   |
              |  整合、决策、生成提示词 |
              +----------+-----------+
                         |
                         v
                       WRITER
                         |
                         v
                      文本输出
                         |
                         v
                    EVALUATOR
                         |
                         v
              +----------------------+
              |   PROMPT ARCHITECT   |
              |       最终决策       |
              +----------+-----------+
                         |
                  +------+------+
                  |             |
                  v             v
                 交付         重新处理
```

上述流程是逻辑关系示意，不代表每个代理都必须参与每一次任务。

Prompt Architect 根据任务复杂度按需调用代理。

所有子代理向主代理提交结果，由主代理负责整合与协调。

# 5. 系统运行流程

系统采用六个主要阶段。

## Phase 1：Task Understanding

理解用户意图、文本功能、目标读者和任务边界。

## Phase 2：Prewriting & Analysis

Prompt Architect 进行初步分析，并根据需要调用 Researcher 和 Logic Analyst。

重点处理：

- 核心认识。
- 材料关系。
- 必要的解释链。
- 信息缺口。
- 判断边界。
- 内容取舍。
- 论证推进方式。

## Phase 3：Prompt Construction

Prompt Architect 根据任务分析结果，动态生成 Writer 的任务提示词。

提示词应当适配具体任务，而不是简单叠加通用规则。

## Phase 4：Writing

Writer 根据任务说明完成文本。

发现问题时可以向主代理反馈，不得擅自改变核心目标。

## Phase 5：Evaluation

Evaluator 对文本进行独立评价。

## Phase 6：Revision & Escalation

Prompt Architect 根据评价决定：

- 局部修改。
- 重新生成提示词。
- 补充资料。
- 重新分析论证。
- 询问用户。
- 暂停当前方案并重新定义问题。

# 6. 共享知识库

系统建立统一的共享知识库。

所有代理都可以根据当前任务读取相关知识，而不是无条件加载全部文件。

知识库主要包括：

| 知识类别 | 主要内容 |
|---|---|
| Philosophy | AI 写作问题的基本认识 |
| Logic | 逻辑关系、因果解释、推理链 |
| Writing | 写作组织、表达、篇章推进 |
| Information | 信息充分性、资料缺口、事实核查 |
| Cases | 成功案例、失败案例、反例 |
| Experiments | 提示词实验与系统测试结果 |
| Decisions | 已接受、已否定和待讨论的设计决策 |

知识状态需要区分：

- Hypothesis：尚待验证的假设。
- Validated Knowledge：经过案例或实验支持的认识。
- Operational Principle：已经转化为实际工作方法的原则。

未经验证的假设不能直接作为强制执行规则。

代理可以提交新知识，但由 Prompt Architect 负责整理、判断和决定是否纳入共享知识库。

# 7. 失败处理机制

系统不能将所有失败都归结为 Writer 的执行问题。

当任务未达到要求时，Prompt Architect 应当重新诊断。

| 失败来源 | 处理方式 |
|---|---|
| 任务理解错误 | 重新澄清用户意图 |
| 信息不足 | 调用 Researcher 或询问用户 |
| 逻辑认识不足 | 调用 Logic Analyst |
| 提示词不合理 | 重新设计任务指令 |
| Writer 执行偏差 | 调整执行要求 |
| 评价标准不合理 | 重新审视评价方法 |
| 原有方案存在缺陷 | 暂停当前方案，重新定义问题 |

系统需要保留失败记录，避免重复尝试已经证明无效的方法。

# 8. 系统设计边界

本系统不追求：

- 让每篇文本都经过完整的多代理流程。
- 通过大量禁用词和句式规则消除 AI 痕迹。
- 无条件增加论证复杂度。
- 将所有潜在问题都写入正文。
- 通过增加免责声明实现表面谨慎。
- 强制每个观点都寻找反对意见。
- 让模型在信息不足时自行补齐逻辑。

本系统追求：

- 正确理解任务。
- 充分利用现有信息。
- 主动识别信息缺口。
- 在必要时向用户提问。
- 建立可靠的认识和论证。
- 根据任务选择适当的表达方式。
- 允许质疑、暂停和重新规划。
- 通过独立评价持续改进。

# 9. 第一阶段开发目标

第一阶段不追求完整实现所有功能，而是验证系统架构是否真正改善写作质量。

优先验证：

1. 写作前准备是否能够改善文本的逻辑完整性。
2. Prompt Architect 的初步分析与动态提示词设计是否有效。
3. Logic Analyst 是否能够发现 Writer 自身没有发现的逻辑问题。
4. Researcher 是否能够有效识别和填补信息缺口。
5. Evaluator 是否能够发现表面流畅但实质存在问题的文本。
6. 多代理协作是否优于直接单代理写作。

初始测试案例：

- 结论替代过程解释。
- 因果机制缺失。
- 自发引入无关反对意见。
- 防御性写作。
- 信息不足时自行补全。
- 概念模糊与抽象表达。
- 整体论证割裂。

最终评价标准不是文本是否更像人类，而是文本是否更加准确、可理解、逻辑充分，并且真正完成了用户的写作任务。

# 10. 总体原则

AI Writing System 的核心原则：

**先理解任务，再判断信息；先形成认识，再组织论证；先设计方法，再执行写作；独立评价结果，必要时重新思考。**

Prompt Architect 负责组织整个过程。

Researcher 负责信息。

Logic Analyst 负责写作前的认识与论证。

Writer 负责文本实现。

Evaluator 负责写作后的独立检验。

所有代理通过共享知识库积累经验，并通过失败案例和实验结果持续修正系统。
