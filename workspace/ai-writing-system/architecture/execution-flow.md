# Execution Flow
## 系统执行流程与任务管理机制

## 1. 设计目的

本文档用于定义 AI Writing System 从接收用户任务到最终交付的完整执行流程。

本系统采用由 Prompt Architect 主导的动态工作流程。

系统不要求所有写作任务遵循完全相同的执行顺序，也不要求每个任务都调用全部子代理。

Prompt Architect 应根据任务性质、复杂程度、信息充分性和潜在风险，决定需要执行哪些环节、调用哪些代理，以及何时停止分析并进入正式写作。

本文件重点规定：

1. 用户任务如何进入系统。
2. Prompt Architect 如何理解和分析任务。
3. 如何判断是否需要补充信息。
4. 如何决定调用哪些子代理。
5. 如何完成写作前准备。
6. 如何生成适配任务的提示词。
7. Writer 如何执行并反馈问题。
8. Evaluator 如何开展独立评价。
9. 修改失败时如何重新规划。
10. 如何判断任务已经完成。

**执行流程的核心不是完成所有阶段，而是确保当前任务所需要的工作得到充分完成。**

---

# 2. 总体执行架构

系统的基本执行流程如下：

```text
                    USER
                      |
                      v
              接收写作任务
                      |
                      v
          +-----------------------+
          |   PROMPT ARCHITECT    |
          |                       |
          | 1. 理解任务           |
          | 2. 初步分析           |
          | 3. 判断信息充分性     |
          | 4. 识别逻辑难点       |
          +-----------+-----------+
                      |
                      v
                判断工作需求
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       无需补充     需要资料     需要深度分析
          |           |           |
          |           v           v
          |       RESEARCHER   LOGIC ANALYST
          |           |           |
          +-----------+-----------+
                      |
                      v
          PROMPT ARCHITECT 整合分析
                      |
                      v
                动态生成提示词
                      |
                      v
                    WRITER
                      |
                      v
                  文本输出
                      |
                      v
                是否需要评价？
                      |
                +-----+-----+
                |           |
                v           v
              不需要       需要
                |           |
                |           v
                |        EVALUATOR
                |           |
                +-----+-----+
                      |
                      v
              PROMPT ARCHITECT
                      |
                      v
                 最终决策
                      |
              +-------+-------+
              |               |
              v               v
            交付文本        重新处理
                              |
                              v
                         诊断问题
                              |
                    +---------+---------+
                    |         |         |
                    v         v         v
                  补充信息  重新分析  调整提示词
                    |         |         |
                    +---------+---------+
                              |
                              v
                           再次写作
```

以上为基本流程示意。

实际执行中，信息检索、逻辑分析和写作可以根据任务需要交替进行。不能将其理解为严格的单向流水线。

# 3. Phase 1：Task Intake（任务接收）

## 3.1 接收用户任务

用户提出写作、修改、分析或重构需求后，Prompt Architect 接收任务。

首先判断用户希望获得什么结果。

常见任务包括：

- 从零开始撰写文本。
- 修改已有文本。
- 重构文章结构。
- 分析现有文本的问题。
- 根据资料组织论证。
- 将零散材料整理为完整文章。
- 讨论写作思路或研究观点。
- 对现有内容进行解释和扩展。

不同任务可能需要完全不同的工作流程。

例如：

用户要求修改一封简短邮件，不需要完整的研究和论证流程。

用户要求根据大量资料撰写一篇分析报告，则需要更充分的写作前准备。

## 3.2 明确任务信息

Prompt Architect 应识别：

| 信息 | 需要明确的内容 |
|---|---|
| Writing Objective | 用户希望完成什么 |
| Text Type | 文本属于什么类型 |
| Text Function | 文本承担什么功能 |
| Audience | 目标读者是谁 |
| Context | 当前文本处于什么背景或位置 |
| Materials | 已有材料有哪些 |
| Constraints | 有哪些明确要求 |
| Completion Criteria | 什么样的结果才算完成 |

不要求每个任务都具备全部信息。

如果某项信息对当前任务并不重要，无须强行补充。

## 3.3 处理任务歧义

如果用户的要求存在多种解释，Prompt Architect 应判断歧义是否会实质影响结果。

如果不会，可以根据上下文作出合理判断。

如果会，应向用户询问。

不要为了形式上的信息完整而频繁打断用户。

---

# 4. Phase 2：Preliminary Analysis（初步分析）

这是 Prompt Architect 必须亲自完成的环节。

不能一开始就把任务交给子代理。

## 4.1 初步理解核心认识

对于需要实质性内容组织的任务，Prompt Architect 应首先判断：

- 当前任务围绕什么问题展开？
- 用户希望表达什么核心认识？
- 现有材料能够支持哪些判断？
- 这些判断之间存在什么关系？
- 哪些内容需要进一步解释？
- 哪些内容尚未得到充分支持？

对于简单文本，可以适当简化这一环节。

## 4.2 初步逻辑分析

Prompt Architect 应主动识别可能存在的逻辑问题。

重点包括：

**认识问题**

是否真正理解了需要表达的内容？

**概念问题**

关键概念是否清晰？是否存在概念混用？

**推理问题**

从已有材料到预期结论，是否存在必要的中间环节？

**因果问题**

是否需要解释某种变化如何产生？是否存在尚未说明的作用过程？

**相关性问题**

当前准备讨论的内容是否真正服务于写作目标？

**不确定性问题**

哪些判断已经有依据？哪些仍然需要验证？

## 4.3 形成初步任务判断

完成初步分析后，Prompt Architect 应形成内部判断：

```text
PRELIMINARY ANALYSIS
│
├── 核心任务
│
├── 核心认识
│
├── 已有材料
│
├── 主要逻辑关系
│
├── 潜在问题
│
├── 信息缺口
│
└── 后续工作建议
```

这份分析用于决定下一步工作，不要求每次都向用户展示。

---

# 5. Phase 3：Information Assessment（信息充分性判断）

Prompt Architect 根据初步分析，判断现有信息是否足以支持任务。

## 5.1 判断信息缺口

信息缺口主要分为以下几类：

| 类型 | 具体表现 | 处理方式 |
|---|---|---|
| 事实缺口 | 缺少必要的事实或数据 | Researcher |
| 资料缺口 | 缺少相关研究或背景资料 | Researcher |
| 文件缺口 | 尚未读取必要的已有文件 | 检索文件 |
| 用户意图缺口 | 无法确定用户真正想表达什么 | 询问用户 |
| 过程信息缺口 | 缺少解释某种现象所需的信息 | Researcher 或用户 |
| 认识缺口 | 已有信息存在，但尚未形成充分理解 | Logic Analyst |
| 论证缺口 | 现有判断之间的关系尚未建立 | Logic Analyst |

需要特别注意：

**信息缺口与认识缺口不是同一个问题。**

前者意味着缺少必要材料，后者意味着尚未充分理解已有材料。

不能通过增加推理来弥补不存在的信息，也不能通过不断检索代替必要的分析。

## 5.2 判断是否需要询问用户

以下情况应优先考虑询问用户：

- 用户的真实意图无法从上下文确定。
- 涉及用户个人经历或未提供的事实。
- 存在多种合理写作方向，且会明显改变结果。
- 核心判断需要用户确认。
- 缺失信息无法通过外部资料或已有文件获得。

如果缺少的信息不影响当前任务，可以继续工作，并保留相应边界。

## 5.3 信息不足时的决策

```text
              发现信息不足
                    |
                    v
             判断缺失的信息
                    |
          +---------+---------+
          |         |         |
          v         v         v
       可检索    需用户确认  无法获得
          |         |         |
          v         v         v
      RESEARCHER   询问用户   保留缺口
          |         |         |
          +---------+---------+
                    |
                    v
               重新判断
```

如果核心任务依赖尚未获得的信息，不得假装已经具备完成条件。

---

# 6. Phase 4：Specialized Analysis（专业分析）

Prompt Architect 根据初步分析和信息判断，决定是否调用 Researcher 和 Logic Analyst。

两个代理可以并行工作，但必须具有相对独立、明确的任务。

## 6.1 Researcher 的调用

适用情况：

- 缺少事实或背景资料。
- 需要核查某项判断。
- 需要寻找相关研究。
- 需要比较不同来源的信息。
- 需要从已有文件中提取内容。
- 需要寻找支持或反驳某种解释的证据。

Researcher 应返回资料报告。

Prompt Architect 不应直接将检索结果全部交给 Writer，而应先判断：

- 哪些材料真正相关？
- 哪些材料能够支持当前论点？
- 哪些材料与原有判断存在冲突？
- 哪些信息仍然不足？

## 6.2 Logic Analyst 的调用

适用情况：

- 核心概念关系不清楚。
- 论证链条较复杂。
- 需要解释因果过程。
- 存在多个竞争性解释。
- 结论与材料之间存在明显距离。
- 需要判断某些讨论是否必要。
- 主代理无法确定当前认识是否充分。

Logic Analyst 应返回逻辑分析报告。

Prompt Architect 需要重点吸收：

- 必要的推理环节。
- 需要进一步解释的关系。
- 不能直接成立的判断。
- 需要补充的信息。
- 可以省略的非必要讨论。

## 6.3 专业分析后的整合

两个代理的报告不应直接拼接。

Prompt Architect 应将它们与自己的初步分析进行比较。

例如：

```text
PROMPT ARCHITECT
       │
       ├── 初步判断：A 导致 B
       │
       ├── RESEARCHER：
       │      发现 A 与 B 的相关资料
       │
       └── LOGIC ANALYST：
              指出 A 到 B 缺少中间过程
                         |
                         v
                主代理重新判断
                         |
                         v
                 是否需要补充资料？
                         |
                  +------+------+
                  |             |
                  v             v
                需要          不需要
                  |             |
                  v             v
               再次检索     进入写作准备
```

如果分析结果仍然无法支持原定结论，主代理应调整论述范围或向用户确认，而不是要求 Writer 强行完成论证。

---

# 7. Phase 5：Prewriting Preparation（写作前准备）

在正式写作之前，Prompt Architect 应根据任务复杂程度，完成必要的写作准备。

这是整个系统区别于直接生成文本的重要环节。

## 7.1 确定核心认识

明确当前文本真正需要表达的内容。

核心认识应当能够回答：

- 文章要解决什么问题？
- 希望读者最终理解什么？
- 当前材料能够支持什么？
- 哪些判断不能超出已有依据？

## 7.2 建立必要的论证关系

对于需要论证的文本，明确主要观点、依据和推理关系。

例如：

```text
核心判断
    |
    v
相关依据
    |
    v
必要解释
    |
    v
推导过程
    |
    v
形成结论
```

这只是可能的论证结构，不要求所有文本都使用相同顺序。

## 7.3 确定解释深度

不是所有内容都需要详细展开。

Prompt Architect 应判断：

- 哪些地方必须解释？
- 哪些地方可以合理省略？
- 哪些过程对读者理解至关重要？
- 哪些解释只会造成重复？
- 哪些因果关系需要展开？
- 哪些关系只需要简单说明？

特别注意不能把「解释得越多」等同于「逻辑越完整」。

## 7.4 明确不确定性

记录：

- 已经确认的内容。
- 可以合理推导的内容。
- 尚未确认的内容。
- 存在其他解释的内容。
- 需要保留的判断边界。

不要把所有不确定性统一转换为免责声明。

## 7.5 确定论述范围

明确哪些内容应该进入文本，哪些内容不应该展开。

防止模型在正式写作时不断引入新的相关问题。

## 7.6 形成写作准备结果

```text
PREWRITING BRIEF
│
├── 写作目的
│
├── 核心认识
│
├── 可用材料
│
├── 主要论证关系
│
├── 必须解释的环节
│
├── 不确定性与信息缺口
│
├── 论述边界
│
└── 预期文本结构
```

这份准备结果将成为动态提示词设计的主要依据。

---

# 8. Phase 6：Prompt Construction（动态提示词设计）

Prompt Architect 根据任务理解、专业分析和写作准备结果，为 Writer 生成专门的任务提示词。

## 8.1 提示词设计原则

提示词必须服务于当前任务。

不要机械套用统一模板，也不要不断增加限制条件。

重点明确：

- Writer 应该完成什么？
- 需要表达什么认识？
- 可以使用什么材料？
- 哪些关系必须得到解释？
- 哪些信息尚未确定？
- 哪些内容不应该擅自扩展？
- 什么样的文本才算完成？

## 8.2 处理提示词中的冲突

如果用户要求之间存在冲突，Prompt Architect 应先判断冲突是否能够通过合理解释解决。

如果不能，应向用户确认或明确取舍依据。

不要将相互矛盾的要求同时交给 Writer。

## 8.3 生成任务说明

具体格式遵循 `communication-protocol.md` 中的 TASK ASSIGNMENT 规范。

对于 Writer，还应提供足够的上下文和写作准备结果。

提示词应当简洁、明确，并保留必要的自主判断空间。

---

# 9. Phase 7：Writing（正式写作）

Writer 接收任务后，开始正式写作。

## 9.1 执行要求

Writer 应当：

1. 准确理解写作目标。
2. 根据文本功能组织结构。
3. 使用已经确认的材料。
4. 建立必要的论证关系。
5. 展开必要的过程和因果解释。
6. 使用符合中文语境的表达方式。
7. 控制无关扩展。
8. 准确处理不确定性。

## 9.2 Writer 的自主反馈

写作过程中，如果 Writer 发现：

- 提示词存在矛盾。
- 现有材料无法支撑论点。
- 论证存在尚未解决的问题。
- 用户的要求存在实质性歧义。
- 当前写作方向可能产生严重问题。

可以暂停当前部分，并向 Prompt Architect 提交反馈。

## 9.3 处理 Writer 的异议

Prompt Architect 收到反馈后，应判断：

- 是否确实存在问题？
- 是否可以自行解决？
- 是否需要调用 Researcher？
- 是否需要调用 Logic Analyst？
- 是否需要询问用户？
- 是否需要调整原有任务说明？

不能要求 Writer 在明知存在实质性问题的情况下，继续生成形式完整但缺乏依据的文本。

---

# 10. Phase 8：Evaluation（独立评价）

文本完成后，Prompt Architect 判断是否需要调用 Evaluator。

## 10.1 调用条件

以下情况建议调用：

- 复杂文章或研究报告。
- 涉及多层论证的文本。
- 对因果解释要求较高的任务。
- 使用大量材料形成的综合性文本。
- 经历多轮修改的文本。
- 用户明确要求严格审查的文本。
- 可能产生较大事实或逻辑风险的文本。

简单且低风险的文本可以由 Prompt Architect 直接检查。

## 10.2 评价重点

Evaluator 重点检查：

1. 是否完成用户任务。
2. 核心认识是否准确。
3. 论证关系是否成立。
4. 必要解释是否充分。
5. 因果关系是否得到恰当说明。
6. 是否存在无依据的推论。
7. 是否存在不必要的论述扩张。
8. 不确定性是否得到准确处理。
9. 中文表达是否自然、清晰。
10. 修改是否产生新的问题。

## 10.3 区分问题严重程度

Evaluator 应区分：

| 等级 | 类型 | 处理方式 |
|---|---|---|
| Critical | 核心事实或论证存在严重问题 | 必须重新处理 |
| Major | 重要解释缺失或整体结构存在缺陷 | 建议修改 |
| Minor | 局部表达、衔接或冗余问题 | 视情况修改 |
| Optional | 不影响任务完成的优化建议 | 不要求修改 |

不能因为文本存在 Minor 或 Optional 问题，就要求全面重写。

---

# 11. Phase 9：Revision（修改与重构）

Prompt Architect 根据评价结果决定修改方式。

## 11.1 先判断问题来源

```text
              发现文本问题
                    |
                    v
                诊断来源
                    |
       +------------+------------+
       |            |            |
       v            v            v
    信息问题     逻辑问题     表达问题
       |            |            |
       v            v            v
    Researcher  Logic Analyst  Writer
```

必要时可以同时调用多个代理。

## 11.2 修改范围

根据问题程度选择：

**局部修改**

适用于不影响整体认识和结构的表达问题。

**段落重构**

适用于论证顺序、解释关系或段落组织存在缺陷的情况。

**整体重写**

适用于核心认识、整体结构或任务理解发生实质性错误的情况。

**重新规划**

适用于原有写作方案本身存在问题的情况。

## 11.3 保留已经成立的内容

修改过程中应明确：

- 哪些内容已经成立？
- 哪些内容需要修改？
- 哪些内容必须保留？
- 修改可能引入什么副作用？

不要因为一个局部问题而无必要地推翻全部内容。

## 11.4 修改后重新评价

如果修改涉及核心论点、论证结构或因果解释，应重新进行相应评价。

如果只是简单修正错别字，不需要重新调用全部代理。

---

# 12. Phase 10：Escalation（问题升级处理）

当当前方案反复失败时，允许跳出原有工作循环。

## 12.1 升级触发条件

包括但不限于：

- 多次修改仍无法解决同一个根本问题。
- 修改一个问题反复产生另一个问题。
- 原有任务目标与可用信息存在根本冲突。
- 提示词本身存在无法通过局部调整解决的问题。
- 代理之间存在持续且无法解决的实质性分歧。
- 当前分析依赖尚未获得的关键信息。
- 原有问题定义可能存在错误。

## 12.2 升级处理流程

```text
             当前方案反复失败
                     |
                     v
               暂停当前工作
                     |
                     v
               定位失败环节
                     |
                     v
               检查原有假设
                     |
                     v
               跳出当前循环
                     |
                     v
               重新讨论问题
                     |
                     v
               形成新的方案
                     |
                     v
               重新分配任务
```

## 12.3 循环之外的讨论

跳出当前循环后，不应继续围绕原有提示词讨论如何增加限制。

应当重新考虑：

- 我们最初对问题的理解是否正确？
- 当前方法为什么会失败？
- 是否存在更根本的问题？
- 是否错误地把一个问题归类为另一个问题？
- 是否需要改变任务拆分方式？
- 是否需要新的信息或不同的分析视角？

如果问题涉及用户的真实意图，应与用户讨论。

## 12.4 记录失败经验

Prompt Architect 应将有价值的失败经验提交到共享知识库。

但必须区分：

- 已经确认的方法缺陷。
- 单次任务中的偶然失败。
- 尚未验证的原因解释。
- 可以推广的操作改进。

不能将单次失败直接转化为普遍规则。

# 13. Phase 11：Completion and Delivery（完成与交付）

系统应当根据任务完成情况决定是否交付。

## 13.1 完成标准

当以下条件得到满足时，可以认为任务已经完成：

- 用户的核心要求已经得到满足。
- 文本功能与任务目标一致。
- 必要信息已经得到使用。
- 重要论证关系已经成立。
- 必要解释已经充分展开。
- 不存在尚未解决的重大事实或逻辑问题。
- 表达符合当前文体和读者需求。

不要求文本达到某种抽象的绝对完美标准。

## 13.2 未解决问题的处理

如果仍然存在无法解决的问题：

- 明确指出问题。
- 说明为什么无法解决。
- 区分已经完成和未完成的部分。
- 不得将未验证内容包装成确定结论。

如果未解决问题不影响核心任务，可以在明确边界的情况下交付。

如果影响核心任务，应先与用户协调。

## 13.3 停止条件

以下情况可以停止：

1. 已经达到用户要求。
2. 进一步修改不会带来实质性改善。
3. 当前问题已经无法通过现有信息解决。
4. 继续修改的预期收益低于其可能产生的副作用。
5. 用户明确要求停止或交付当前版本。

**完成任务比无限优化文本更加重要。**

# 14. Adaptive Execution（动态执行机制）

整个系统不应将上述阶段理解为必须依次执行的固定流程。

Prompt Architect 应根据任务选择适当路径。

## 14.1 简单写作任务

# 15. Execution State（任务状态管理）

为了避免代理之间重复工作，Prompt Architect 应当在任务执行期间维护必要的状态信息。

建议采用以下状态：

| 状态 | 含义 |
|---|---|
| RECEIVED | 已接收任务 |
| UNDERSTANDING | 正在理解任务 |
| ANALYZING | 正在进行初步分析 |
| WAITING_FOR_INFORMATION | 等待资料或用户反馈 |
| RESEARCHING | 正在检索资料 |
| LOGIC_ANALYSIS | 正在进行逻辑分析 |
| PREPARING | 正在进行写作前准备 |
| WRITING | 正在正式写作 |
| EVALUATING | 正在独立评价 |
| REVISING | 正在修改 |
| ESCALATED | 已暂停当前方案并进入重新讨论 |
| COMPLETED | 已完成并交付 |

状态管理用于追踪当前工作，不要求每次状态变化都生成独立文件。

每次重新分配任务时，应保留必要的上下文，避免代理反复分析已经解决的问题。

---

# 16. Shared Knowledge Integration（共享知识库整合）

执行过程中，各代理可能发现值得保留的新知识。

Prompt Architect 应在以下时机考虑知识库更新：

- 发现新的典型问题。
- 获得有价值的反例。
- 发现原有写作原则存在适用边界。
- 验证某种修改方法有效或无效。
- 发现代理协作中的系统性缺陷。
- 发现提示词设计产生了预期之外的副作用。

知识提交遵循 `communication-protocol.md` 的 KNOWLEDGE_PROPOSAL 规范。

知识更新不应打断正常写作任务。

对于尚未验证的观察，应先记录为待验证假设，而不是立即改变所有代理的行为。

---

# 17. 最终执行原则

整个系统遵循以下原则：

1. 先理解任务，再决定如何工作。
2. Prompt Architect 必须进行初步分析。
3. 根据实际问题决定是否调用专业代理。
4. 信息缺失时优先检索或询问，不得自行编造。
5. 正式写作前，完成当前任务所必需的认识和论证准备。
6. 提示词根据任务动态生成，不机械套用固定规则。
7. Writer 可以质疑任务，但不能擅自改变用户目标。
8. Evaluator 独立评价最终文本。
9. 发现问题先诊断，再决定修改方式。
10. 必要时暂停当前方案，在原有循环之外重新讨论。
11. 所有代理共享知识库，但未经验证的观察不得直接变成强制规则。
12. 达到任务完成标准后，应当停止修改并交付。

**本系统的执行目标不是让所有代理完成预设流程，而是让每个必要的认知环节得到恰当处理，并确保整个写作过程能够根据实际问题不断调整。**
