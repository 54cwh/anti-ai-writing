# Writing Workflow
## 写作工作流程与代理协作机制

## 1. 设计目的

Writing Workflow 是 AI Writing System 的整体工作流程定义文件。

它负责将任务理解、信息获取、认识分析、提示词设计、文本生成、质量评价和迭代修订组织成一套完整的工作机制。

本系统采用 Prompt Architect 作为主代理，其他专业代理作为子代理。

Prompt Architect 负责整个任务的组织和协调，并根据不同阶段的工作需要，向相应代理分配任务。

本系统的核心工作流程包括：

1. 理解用户的写作任务。
2. 明确写作目标和实际需求。
3. 判断现有资料是否足够。
4. 组织必要的信息检索。
5. 进行写作前的认识与论证分析。
6. 形成明确的写作方案。
7. 设计 Writer 的专属提示词。
8. 执行正式写作。
9. 对完整文本进行整体评价。
10. 根据问题来源组织修订。
11. 判断是否需要进一步分析或询问用户。
12. 完成文本交付。

本文件重点解决：

- 不同代理应该在什么阶段参与？
- Prompt Architect 如何组织任务？
- 如何判断是否需要进行写作前分析？
- 如何判断现有信息是否足以支持写作？
- 如何设计适合具体任务的 Writer Prompt？
- Writer 什么时候可以开始写作？
- 如何处理写作过程中的质疑和信息请求？
- Evaluator 如何参与质量控制？
- 如何避免反复进行无效修改？
- 如何根据任务复杂程度调整工作流程？

**本文件的最终目标，是让系统形成一套稳定、灵活、可执行的中文写作工作流程，使写作建立在充分的任务理解、必要的信息准备和明确的认识基础之上。**

## 2. 系统总体架构

### 2.1 主代理与子代理

Prompt Architect 是整个系统的主代理。

它负责：

- 接收用户任务。
- 理解用户意图。
- 确定任务范围。
- 判断任务复杂程度。
- 组织信息检索。
- 协调 Logic Analyst。
- 形成写作方案。
- 设计 Writer Prompt。
- 调度 Writer。
- 调度 Evaluator。
- 组织修订。
- 管理用户交互。
- 决定任务何时完成。

其他代理承担专业工作。

| 代理 | 主要职责 | 参与阶段 |
|---|---|---|
| Prompt Architect | 任务理解、提示词设计、流程协调 | 全流程 |
| Logic Analyst | 认识分析、概念分析、论证与因果分析 | 写作前及必要的修订阶段 |
| Researcher | 信息检索、资料核查、证据补充 | 写作前及必要的修订阶段 |
| Writer | 中文文本生成与修改 | 正式写作及修订阶段 |
| Evaluator | 完整文本评价、缺陷诊断 | 写作后及修订阶段 |

Prompt Architect 始终负责工作流程的协调。

子代理可以提出建议、质疑和替代方案，但不能自行改变用户的核心任务目标。

## 3. 任务接收与理解

用户提出任务后，Prompt Architect 首先负责理解任务。

此阶段不要求立即生成 Writer Prompt。

### 3.1 识别写作任务

明确：

- 用户需要什么类型的文本？
- 文本用于什么场景？
- 目标读者是谁？
- 用户希望解决什么问题？
- 最终需要交付什么？
- 是否存在明确的篇幅、格式和文体要求？

### 3.2 理解用户的真实意图

需要识别用户真正希望完成的事情。

例如：

用户要求「帮我分析这段文字」。

可能涉及：

- 语言问题。
- 逻辑问题。
- 论证结构。
- 内容准确性。
- 整体写作质量。

如果上下文已经明确，应直接采用已有认识。

如果存在会显著影响结果的歧义，应向用户询问。

### 3.3 识别任务边界

明确：

- 哪些内容必须保留？
- 哪些内容允许调整？
- 是否允许补充外部资料？
- 是否允许提出新的观点？
- 是否允许改变文章结构？
- 是否需要保留用户原有表达习惯？

### 3.4 形成 Task Brief

Prompt Architect 根据任务理解形成 Task Brief。

建议包含：

```markdown
# Task Brief

## 1. Task
具体写作任务。

## 2. Purpose
写作目的。

## 3. Audience
目标读者。

## 4. Genre
文体要求。

## 5. Core Objective
核心写作目标。

## 6. Required Content
必须包含的内容。

## 7. Constraints
篇幅、格式、资料及其他限制。

## 8. Available Materials
现有资料。

## 9. User Preferences
用户明确表达的偏好。

## 10. Open Questions
尚未解决的问题。
```

简单任务可以直接在内部形成简化版本。

复杂任务应保留完整记录。

## 4. 任务复杂度判断

不同任务需要不同程度的准备。

如果每项简单任务都调用全部代理，系统会产生大量不必要的分析。

Prompt Architect 应当根据任务性质选择工作流程。

### 4.1 简单任务

例如：

- 修改一段通知。
- 润色一封邮件。
- 调整句子表达。
- 将已有材料整理成完整段落。
- 根据明确要求撰写简短说明。

特点：

- 任务目标明确。
- 资料已经充分。
- 不涉及复杂的新判断。
- 不需要建立新的论证。

处理方式：

```text
用户任务
   |
   v
Prompt Architect 理解任务
   |
   v
生成 Writer Prompt
   |
   v
Writer 执行
   |
   v
必要的质量检查
   |
   v
交付
```

此类任务通常不需要调用 Logic Analyst。

### 4.2 中等复杂度任务

例如：

- 撰写活动总结。
- 整理一份工作报告。
- 根据多份资料形成分析文章。
- 撰写具有明确观点的短文。
- 对已有内容进行结构性修改。

特点：

- 需要组织多项信息。
- 需要判断内容之间的关系。
- 可能涉及局部论证。
- 对文章结构存在一定要求。

处理方式：

根据需要调用 Researcher 或 Logic Analyst。

完成必要准备后，由 Writer 执行。

### 4.3 高复杂度任务

例如：

- 学术论文。
- 研究报告。
- 政策分析。
- 深度评论文章。
- 需要建立复杂解释框架的长篇文章。

特点：

- 涉及多个概念和论证环节。
- 需要外部资料或专业知识。
- 可能存在多个竞争性解释。
- 对事实、推理和结论的对应关系要求较高。
- 写作前需要形成较完整的认识。

处理方式：

必须进行必要的写作前分析。

根据任务需要调用 Researcher 和 Logic Analyst。

完成分析后，由 Prompt Architect 设计 Writer Prompt。

### 4.4 复杂度判断的动态调整

任务复杂度并非一经确定就不能改变。

例如：

原本只需要润色一段话，但 Writer 发现原文存在严重的因果解释问题。

此时可以将任务升级为中等或高复杂度任务。

反过来，如果复杂任务经过分析后发现只需要整理已有资料，也可以减少后续代理参与。

## 5. 写作前准备

写作前准备是整个系统的重要环节。

Prompt Architect 应当根据任务要求，判断是否需要进行信息获取和认识分析。

### 5.1 检查现有信息

首先明确当前系统已经掌握什么。

包括：

- 用户提供的材料。
- 当前对话中的信息。
- 共享知识库中的相关内容。
- 已有的研究成果。
- 可以直接使用的可靠资料。

避免重复询问用户已经提供的信息。

### 5.2 识别信息缺口

判断完成任务还需要什么信息。

例如：

- 某项事实尚未核实。
- 缺少具体案例。
- 缺少必要的背景资料。
- 缺少某个专业概念的定义。
- 缺少用户的真实经历。
- 缺少用户希望表达的具体观点。

### 5.3 制定信息获取计划

如果需要外部资料，Prompt Architect 向 Researcher 分配任务。

Researcher 应明确：

- 检索目的。
- 需要获取的信息。
- 资料来源要求。
- 资料使用范围。
- 仍然无法获得的内容。

检索结果应当回到 Prompt Architect，由其判断是否足以支持后续分析。

### 5.4 判断是否需要询问用户

如果缺少的信息只有用户能够提供，应当主动询问。

例如：

- 用户希望表达的真实立场。
- 用户经历的具体过程。
- 尚未公开的内部材料。
- 用户对不同方案的选择。
- 会影响任务方向的重要背景。

在获得回答之前，可以继续不依赖这些信息的工作。

### 5.5 形成 Information Brief

```markdown
# Information Brief

## 1. Available Information
已经获得的信息。

## 2. Required Information
完成任务所需的信息。

## 3. Information Gaps
尚未获得的信息。

## 4. Retrieved Materials
已经检索到的资料及其来源。

## 5. Reliability
资料的可靠程度及使用限制。

## 6. User Input Required
需要用户提供或确认的内容。

## 7. Unresolved Questions
仍然无法解决的问题。
```

## 6. 写作前认识与论证分析

完成必要的信息准备后，Prompt Architect 判断是否需要 Logic Analyst 参与。

对于复杂写作任务，Logic Analyst 应当承担重要的前置分析工作。

### 6.1 明确讨论对象

Logic Analyst 需要理解：

- 文章究竟讨论什么？
- 核心概念分别指向什么？
- 涉及哪些主体？
- 需要解释什么现象？
- 不同对象之间存在什么关系？

### 6.2 形成核心认识

判断：

- 当前已经能够确定什么？
- 哪些内容属于事实？
- 哪些内容属于解释？
- 哪些内容仍然属于假设？
- 哪些判断需要进一步验证？

### 6.3 分析论证关系

检查：

- 核心观点是什么？
- 观点依赖哪些前提？
- 需要哪些证据？
- 不同判断之间如何联系？
- 是否存在必要的解释环节？
- 结论是否超出了现有材料能够支持的范围？

### 6.4 重点检查因果解释

当文章涉及因果关系时，需要明确：

- 发生了什么变化？
- 哪些因素可能影响这一变化？
- 相关因素通过什么过程发挥作用？
- 这些因素之间是否存在其他可能的关系？
- 当前解释是否具有足够依据？

这里的因果分析不限于经济学或科学研究。

日常写作中的行为解释、事件描述、政策分析、人物动机和组织管理，同样可能存在因果关系。

例如：

「加强管理后，团队工作效率明显提高。」

需要判断：

- 管理方式具体发生了什么变化？
- 团队成员的行为是否因此改变？
- 工作流程发生了什么变化？
- 效率提高是否能够归因于管理措施？

根据任务需要决定解释深度。

### 6.5 识别潜在问题

Logic Analyst 应当主动检查：

- 是否遗漏了重要前提？
- 是否存在推理跳跃？
- 是否将相关关系直接解释为因果关系？
- 是否忽略了其他合理解释？
- 是否存在概念混用？
- 是否存在未经解释的判断？
- 是否有意外引入无关的反对意见？

### 6.6 形成 Reasoning Brief

```markdown
# Reasoning Brief

## 1. Main Question
需要回答的核心问题。

## 2. Core Understanding
当前形成的主要认识。

## 3. Key Concepts
核心概念及其含义。

## 4. Main Arguments
主要论点。

## 5. Reasoning Relations
论点之间的联系。

## 6. Causal Explanations
涉及的因果关系及其解释。

## 7. Supporting Evidence
支持主要判断的资料。

## 8. Alternative Explanations
需要考虑的其他解释。

## 9. Uncertainties
尚未解决的问题。

## 10. Writing Implications
对正式写作的具体要求。
```

对于简单任务，不需要强制生成完整的 Reasoning Brief。

## 7. 写作准备完成判断

这是整个工作流程的重要决策点。

Prompt Architect 应当判断当前是否具备开始正式写作的条件。

### 7.1 任务是否清楚

是否已经明确：

- 写作目的。
- 文章类型。
- 核心内容。
- 目标读者。
- 主要限制。

### 7.2 认识是否足够

对于需要分析的任务，是否已经明确：

- 讨论对象。
- 核心概念。
- 主要观点。
- 必要的论证关系。
- 需要解释的关键过程。

### 7.3 资料是否足够

是否已经获得完成当前任务所需的主要信息？

如果资料不足，是否已经明确：

- 哪些内容可以写？
- 哪些内容需要保留？
- 哪些内容不能推断？
- 是否需要进一步检索或询问用户？

### 7.4 写作方向是否明确

Writer 是否能够理解：

- 应当写什么？
- 为什么这样写？
- 需要重点解释什么？
- 哪些内容需要保留？
- 哪些内容不应擅自扩展？

### 7.5 是否存在尚未处理的核心问题

如果存在会改变核心观点或论证方向的问题，应当先处理。

如果剩余问题不影响当前任务，可以在明确边界的情况下开始写作。

### 7.6 准备完成状态

建议设置三种状态：

**READY**

任务理解、信息准备和必要的认识分析已经达到当前任务所需程度，可以开始写作。

**READY WITH LIMITATIONS**

仍有部分信息缺口或不确定性，但已经明确其范围，不妨碍完成当前任务。

**NOT READY**

存在影响核心内容的重要问题，需要继续检索、分析或询问用户。

```text
写作准备检查
      |
      v
任务是否清楚？
      |
      v
认识是否充分？
      |
      v
资料是否足够？
      |
      v
是否存在未解决的核心问题？
      |
      +------------------+
      |                  |
      v                  v
      是                 否
      |                  |
      v                  v
继续准备             判断剩余限制
                         |
                  +------+------+
                  |             |
                  v             v
              不影响写作      影响写作
                  |             |
                  v             v
               READY        NOT READY
                  |
                  v
                写作
```

这里的充分程度应当根据任务确定。

系统不需要在写作前消除所有不确定性。

## 8. Prompt Architect 的提示词设计

这是本系统最重要的工作之一。

Prompt Architect 不应当简单地将用户原始要求转发给 Writer。

它需要根据前面的工作成果，为具体任务设计 Writer Prompt。

### 8.1 提示词的设计目标

Writer Prompt 应当让 Writer 明确：

- 当前任务是什么？
- 写作目的是什么？
- 需要解决什么问题？
- 已经形成了哪些认识？
- 可以使用哪些资料？
- 文章应当如何组织？
- 哪些内容需要充分解释？
- 哪些信息不能自行补充？
- 遇到困难时应当如何反馈？

### 8.2 提示词的基本组成

```markdown
# Writer Prompt

## 1. Task
明确写作任务。

## 2. Purpose
明确写作目的。

## 3. Audience and Genre
明确读者和文体。

## 4. Core Understanding
提供已经形成的主要认识。

## 5. Main Arguments
提供需要展开的核心论点。

## 6. Information and Evidence
提供可使用的资料及其来源。

## 7. Writing Direction
明确文章的组织方向。

## 8. Expression Guidance
明确中文表达要求。

## 9. Required Content
明确必须包含的内容。

## 10. Constraints
明确事实、观点、篇幅及任务边界。

## 11. Uncertainties
说明尚未解决的问题及其处理方式。

## 12. Expected Output
明确最终交付形式。

## 13. Escalation
说明遇到哪些问题时应暂停并向主代理反馈。
```

根据任务复杂程度，可以删减或合并部分内容。

### 8.3 正向指令优先

提示词设计应当明确告诉 Writer 如何完成任务。

例如：

应当告诉 Writer：

「介绍政策实施过程时，按照实际发生的时间顺序说明政策背景、实施主体、具体措施和实施结果。不同环节之间存在因果联系时，说明相应的作用过程。」

这比单纯要求：

「避免空洞表达，不要出现逻辑跳跃。」

更具有可执行性。

否定性指令用于补充必要的边界。

### 8.4 提供足够的认识基础

Writer Prompt 应当包含必要的 Reasoning Brief。

Writer 需要理解文章的主要论证关系。

如果只提供结论和段落标题，Writer 很容易自行填补缺失的推理过程。

### 8.5 根据具体任务设计提示词

不能使用一套固定提示词处理所有写作任务。

例如：

学术论文需要强调概念、证据、研究方法和论证关系。

活动总结需要强调实际过程、参与情况、活动成果和表达目的。

个人陈述需要强调真实经历、个人认识和申请目标之间的联系。

Prompt Architect 应当根据任务生成专属提示词。

### 8.6 提示词本身需要检查

正式提交给 Writer 之前，Prompt Architect 应当检查：

- 任务是否明确？
- 上下文是否充分？
- 不同要求之间是否存在冲突？
- 是否遗漏关键认识？
- 是否提供了必要资料？
- 是否明确表达了正向写作方向？
- 是否保留了用户的任务边界？
- Writer 是否能够据此独立开展工作？

## 9. Writer 正式写作

Writer 在收到 Prompt Architect 提供的 Writer Prompt 后开始正式写作。

### 9.1 理解写作任务

Writer 首先需要理解：

- 写作目的。
- 核心观点。
- 主要论证。
- 目标读者。
- 表达要求。

### 9.2 根据认识组织文本

Writer 应当依据 Reasoning Brief 组织文章。

根据实际内容决定：

- 从什么问题切入。
- 如何安排主要观点。
- 哪些地方需要解释。
- 哪些地方需要补充事实。
- 如何连接不同段落。

### 9.3 将认识转化为中文表达

Writer 应遵循 Chinese Expression 的要求。

重点关注：

- 概念与实际对象之间的对应关系。
- 词语与真实含义之间的对应关系。
- 句子与实际认识之间的对应关系。
- 段落与论证过程之间的对应关系。

### 9.4 处理写作中的新问题

Writer 在写作过程中可能发现：

- 原有认识仍然不充分。
- 某项资料无法支持预期表达。
- 不同论点之间存在冲突。
- 某种表达会改变原意。
- 当前结构无法合理容纳已有内容。

Writer 可以：

1. 提出质疑。
2. 请求补充资料。
3. 提出替代方案。
4. 说明潜在问题。
5. 请求 Logic Analyst 重新分析。

Writer 应向 Prompt Architect 提交具体反馈。

### 9.5 保持任务边界

Writer 可以提出新的观点或结构方案。

但未经 Prompt Architect 协调，不得自行改变：

- 用户的核心目标。
- 文章的主要讨论范围。
- 用户明确表达的立场。
- 已经确认的任务要求。

### 9.6 完成文本

Writer 应当提交完整文本。

对于复杂任务，还应当说明：

- 哪些内容依据现有资料完成。
- 哪些地方存在不确定性。
- 哪些问题仍未解决。
- 是否需要进一步处理。

---

## 10. 写作后整体评价

Writer 完成文本后，Prompt Architect 将文本及必要上下文交给 Evaluator。

Evaluator 应当独立阅读完整文本。

### 10.1 提供评价材料

包括：

- 原始 Task Brief。
- Writing Brief。
- Reasoning Brief。
- 相关资料。
- Writer 完成的文本。

### 10.2 整体评价

Evaluator 检查：

- 是否完成原始任务？
- 核心认识是否准确？
- 论证关系是否成立？
- 重要因果解释是否充分？
- 语言是否准确自然？
- 段落组织是否合理？
- 读者能否理解全文？

### 10.3 缺陷诊断

对发现的问题进行定位。

说明：

- 问题出现在哪里？
- 具体表现是什么？
- 为什么构成问题？
- 问题可能来自哪个环节？
- 对文章整体质量有什么影响？

### 10.4 形成 Evaluation Brief

Evaluator 将评价结果提交给 Prompt Architect。

Prompt Architect 根据评价结果决定是否需要修订。

---

## 11. 修订与反馈

修订应当根据问题来源进行。

### 11.1 语言问题

由 Writer 修改。

例如：

- 词语搭配不自然。
- 抽象表达缺少必要解释。
- 句子组织不合理。
- 局部段落存在重复。

### 11.2 认识问题

交由 Logic Analyst 重新分析。

例如：

- 核心概念使用不准确。
- 重要前提缺失。
- 不同观点之间存在冲突。
- 原有解释无法成立。

### 11.3 信息问题

交由 Researcher 补充资料。

例如：

- 事实缺少依据。
- 数据需要核实。
- 案例信息不完整。
- 关键背景尚未获得。

### 11.4 结构问题

由 Prompt Architect 重新组织写作任务，再交由 Writer 调整。

### 11.5 任务理解问题

由 Prompt Architect 重新检查原始 Task Brief。

涉及用户真实意图或核心目标变化时，需要向用户确认。

### 11.6 修订后的复核

Writer 完成修订后，Evaluator 重新检查。

重点确认：

- 原有问题是否真正解决？
- 是否产生新的问题？
- 是否损害已经成立的内容？
- 整体文本是否得到改善？

---

## 12. 问题升级与循环之外讨论

如果多轮修订仍然无法解决问题，Prompt Architect 应当启动升级机制。

### 12.1 判断是否存在局部优化循环

检查：

- 是否反复修改同一问题？
- 是否出现问题转移？
- 是否始终没有增加新的认识？
- 是否存在相互冲突的要求？
- 是否出现多个代理持续分歧？

### 12.2 暂停当前工作

保留：

- 当前文本。
- 已经完成的分析。
- 历史修改记录。
- 尚未解决的问题。

### 12.3 建立独立分析任务

重新组织问题。

根据需要调用：

- Logic Analyst。
- Researcher。
- 其他适当的独立分析代理。

### 12.4 形成新的解决方案

由 Prompt Architect 判断：

- 是否需要重新分析？
- 是否需要补充资料？
- 是否需要调整提示词？
- 是否需要询问用户？
- 是否需要缩小任务范围？

### 12.5 恢复工作

将新的解决方案转化为具体任务，再交给相关代理执行。

详细机制遵循《09-escalation-and-human-interaction.md》。

## 13. 共享知识库的使用

所有代理应当使用统一的共享知识库。

共享知识库负责保存跨任务具有持续价值的认识、方法、经验和工作记录。

### 13.1 使用原则

- 所有代理可以读取与当前任务相关的知识。
- 各代理按照自身职责使用知识库。
- 新知识应当经过适当整理再写入。
- 不应将未经验证的临时判断直接作为确定知识保存。
- 不同来源和可信程度的信息应当有所区分。

### 13.2 写作前使用

Prompt Architect 在任务开始时，可以检索：

- 相关写作方法。
- 用户已经确认的表达要求。
- 以前处理过的类似问题。
- 已经形成的分析结论。
- 相关研究资料。

Logic Analyst 可以查阅已有的概念和论证分析。

Researcher 可以利用已有资料和检索记录。

### 13.3 写作后使用

Evaluator 可以记录：

- 重复出现的表达问题。
- 常见的推理缺陷。
- 反复出现的语言问题。
- 有效的修订方法。
- 尚未解决的系统性问题。

### 13.4 避免知识库污染

知识库应当区分：

- 已确认的事实。
- 专业知识。
- 方法建议。
- 工作假设。
- 未经验证的观点。
- 历史任务记录。

不同类别不能混为一谈。

详细规范遵循共享知识库的专门设计文件。

## 14. 任务状态管理

Prompt Architect 应当维护当前任务的状态。

建议设置以下状态：

| 状态 | 含义 |
|---|---|
| INTAKE | 接收任务 |
| UNDERSTANDING | 任务理解 |
| RESEARCHING | 信息获取 |
| ANALYZING | 写作前分析 |
| PREPARING | 写作方案与提示词设计 |
| READY | 已具备写作条件 |
| WRITING | 正式写作 |
| EVALUATING | 整体质量评价 |
| REVISING | 修订 |
| ESCALATED | 问题升级 |
| WAITING_USER | 等待用户提供信息或确认 |
| COMPLETED | 任务完成 |

任务状态应当反映实际工作情况。

例如：

如果 Writer 正在等待 Researcher 补充资料，不能将任务标记为 READY。

如果任务需要用户确认核心观点，应当进入 WAITING_USER。

如果已经形成完整文本，但仍有重要缺陷，应当继续保持在 EVALUATING 或 REVISING 阶段。

## 16. 主代理的工作规范

Prompt Architect 作为主代理，需要遵循以下工作要求。

### 16.1 负责整体任务

Prompt Architect 必须始终掌握：

- 当前任务目标。
- 当前工作阶段。
- 各代理的工作结果。
- 尚未解决的问题。
- 下一步需要执行的任务。

### 16.2 根据需要调度代理

不应机械调用所有代理。

应根据实际任务判断是否需要：

- Researcher。
- Logic Analyst。
- Writer。
- Evaluator。

### 16.3 负责提示词质量

每次调用子代理时，应提供明确的任务。

提示词需要包含必要的背景、目标、材料和工作边界。

### 16.4 负责协调不同意见

当不同代理出现分歧时，应当判断：

- 分歧来自事实理解？
- 分歧来自推理过程？
- 分歧来自表达偏好？
- 分歧来自任务要求？

根据问题来源组织后续工作。

### 16.5 负责用户交互

当任务需要用户补充信息或作出决定时，Prompt Architect 应主动询问。

### 16.6 负责最终交付判断

Prompt Architect 根据 Evaluator 的意见、用户要求和实际任务情况决定是否完成。

不能仅凭 Writer 声称已经完成，就直接结束复杂任务。

---

## 17. 最终交付与任务结束

任务结束前，Prompt Architect 应当进行最终检查。

### 18.1 任务完成

确认最终文本符合用户的核心要求。

### 18.2 内容准确

重要事实、概念和引用具有相应依据。

### 18.3 论证合理

核心判断具有必要的解释和支持。

### 18.4 语言清晰

读者能够理解文章主要表达的内容。

### 18.5 结构合理

不同部分能够形成合理的整体组织。

### 18.6 不确定性得到处理

尚未解决的问题已经明确说明。

### 18.7 用户要求得到满足

最终交付形式符合用户要求。

如果仍存在无法解决的问题，应当明确告知用户。

不能为了形式上的完成而隐藏重要缺陷。

## 18. 最终设计原则

Writing Workflow 遵循以下原则：

1. Prompt Architect 是主代理，负责整个工作流程。
2. Writer 是执行文本生成任务的专业子代理。
3. Logic Analyst 主要负责写作前的认识与论证分析。
4. Researcher 主要负责信息获取和资料核查。
5. Evaluator 主要负责写作后的整体质量评价。
6. 根据任务复杂程度决定代理参与方式。
7. 不要求所有任务经过相同的分析流程。
8. 写作前应当检查任务理解、信息和认识准备情况。
9. 复杂写作任务应当进行必要的写作前分析。
10. Prompt Architect 应当根据具体任务设计 Writer Prompt。
11. 正向指令承担主要的行为引导功能。
12. Writer 应当获得充分的任务背景和认识基础。
13. Writer 可以质疑、请求资料和提出替代方案。
14. Writer 不得未经协调改变用户的核心任务目标。
15. Evaluator 应当独立评价完整文本。
16. 修订应当根据问题来源进行。
17. 发现局部优化循环时，应当允许暂停当前工作。
18. 必要时在循环之外重新讨论问题。
19. 缺少用户信息时，应当主动询问。
20. 所有代理应当合理使用共享知识库。
21. 不确定性应当得到明确处理。
22. 根据实际任务建立合理的停止条件。

**AI Writing System 的工作流程，应当让每个代理在合适的阶段承担合适的工作。正式写作需要建立在明确的任务、充分的必要信息和已经形成的认识之上。最终文本应当准确传达这些认识，并经受整体质量评价。**
